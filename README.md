# ArchMaths (C++ revision)

ArchMaths is a graphing calculator. This repository holds the C++ revision:
a Qt desktop app (`src/`, `include/`, `resources/`), the single-file web app
`arch-current.html`, and a standalone WebAssembly compute core (`wasm/`) that
accelerates the web app's arithmetic.

## WebAssembly compute core

The web app runs its own JavaScript engine, with hot paths offloaded to a
wasm module that is built from this repository and embedded base64-inline
into `arch-current.html` (the `<!-- ARCHCORE:BEGIN/END -->` block — never
edit it by hand; it is regenerated by `wasm/build.sh --embed`).

Architecture:

- `src/math/Tokenizer.*` / `src/math/ExpressionParser.*` — shared parsers
  with three dialects: `Math` (native calculator syntax), `JsSubset` (the
  arithmetic JS subset the page transpiles plot bodies to), and `CalcJs`
  (the page's scalar calcJS expression syntax, ported line-by-line).
- `wasm/core/ExprProgram.*` — expression → AST → hash-consed DAG (constant
  folding + CSE) → linear bytecode, interpreted 256 lanes per block.
  Anything the core cannot evaluate exactly fails compilation and the page
  keeps its JS path.
- `wasm/core/CoreApi.cpp` — C ABI (currently **ABI v2**): program handles,
  `ac_compile`/`ac_eval`, scalar entry points `ac_calc_compile` /
  `ac_calc_eval1`, and the kernel entry points below.
- `wasm/core/kernels/` — algorithm kernels ported line-by-line from the
  page (floating-point operation order preserved): function-plot samplers
  (`explicit2d`, `implicit2d`, `surface3d`, `flat3d`, `mc3d`), the builtin
  advanced functions (`advfuncs`), scalar expression evaluation
  (`CalcJsCompiler`), numeric root finding (`rootfind`), and the full
  geometry engine (`geometry*.cpp` — all 28 `geometryType`s: points,
  intersections, constructions, conics, measurements, tangent, fitline,
  with the page's fixed-point iteration semantics).
- `wasm/js/archcore.js` + `wasm/js/kernels/*.js` — loader and adapters.
  Every kernel is registered under `ArchCore.kernels.*` and guarded; any
  failure (unsupported syntax, modified builtins, probe mismatch) falls
  back to the original JS path. Programs are additionally verified at
  runtime (first-use probe, 1e-9 tolerance, permanent reject on mismatch).
  `localStorage["archcore-enabled"] = "0"` disables wasm entirely.

Compatibility notes (hard requirements, all covered by tests):

- **JS custom functions**: simple expression-body functions are inlined at
  wasm compile time; advanced JavaScript-body functions (and user-redefined
  builtins) make the affected expression ineligible and transparently take
  the JS path, producing identical results.
- **`[A,x]` coordinate references** stay a parse-time text substitution
  (`resolvePointCoords` / `reResolveAllPointCoordsEntries`); the wasm core
  only ever sees the substituted string, and drags refresh through the
  same chain as before.
- **`name=root[expr, var, init]`** entry parsing is unchanged; the numeric
  solver (bracket scan → Newton/bisection hybrid) is ported bit-exactly.

## Building

Desktop app: see `CLAUDE.md` (CMake + Qt6).

Wasm core and web page:

```bash
bash wasm/build.sh                # -> wasm/dist/archcore.wasm
ARCHCORE_HTML=arch-current.html bash wasm/build.sh --embed   # inline into page
```

Toolchain: `zig c++` targeting wasm32-wasi (reactor mode). Set `ZIG=...` or
`pip install ziglang`. On hosts that cannot run the prebuilt zig binary
(e.g. HarmonyOS PC), a locally-built clang + wasi-sdk behind a `zig c++`
shim works; make sure floating-point contraction is disabled
(`-ffp-contract=off`) so results match V8 bit-for-bit.

## Testing

Node-side differential suites (wasm vs the page's own JS, extracted from
`arch-current.html`), each exits non-zero on failure:

```bash
node wasm/tests/vm-diff.mjs        # expression VM vs page JS
node wasm/tests/loops-diff.mjs     # sum/prod/int large operators
node wasm/tests/advfuncs-diff.mjs  # builtin advanced functions
node wasm/tests/calcjs-diff.mjs    # CalcJs scalar dialect vs calcJSUtils
node wasm/tests/rootfind-diff.mjs  # root[] solver vs page algorithm
node wasm/tests/geometry-*-check.mjs   # geometry kernels, analytic cases
```

Browser-side differential tests live in `wasm/tests/browser/` and drive the
real page through a CDP bridge (`node wasm/tests/browser/cdp.js run
<tabUrlSubstring> @<script>`). Note:

- `explicit2d.js` and `loops.js` use `setTimeout(0)` yields and contain
  benchmark sections; on browsers that intensively throttle background-tab
  timers they appear to hang. Use `explicit2d-nobench.js` /
  `loops-nobench.js` (microtask yields, benchmarks stripped) there.
- If the bridge drops the `Runtime.evaluate` response under console load,
  use `wasm/tests/browser/run-poll.sh <test> <name>`, which stores the
  result on `window.__testResult` and polls for it instead.
- Known, documented difference: `y=int(exp(-t^2),t,0,x)` under the
  autoBreak/adaptive plot branches produces slightly different vertex
  counts between JS and wasm — last-ulp libm differences amplified by
  adaptive step-size decisions (the naive branch matches bit-for-bit).

## Layout

- `arch-current.html` — the web app (embedded wasm block + kernel guards).
- `wasm/` — core sources, kernels, JS adapters, embed script, tests.
- `web/` — alternate wasm shell/packaging experiments.
- `src/`, `include/`, `resources/` — Qt desktop app.
